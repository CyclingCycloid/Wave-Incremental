# 代码整理与候选实现方案

状态：修改前方案；未改游戏代码。此文档规定后续整理的边界，防止把数值公式“整理”成另一套玩法。

## 候选目录

实施时按主题建立 Review/AutoBuy/、Review/Offline/、Review/Numerics/、Review/SaveAndRules/。每个目录至少包含：

1. 该主题的候选代码或原文件副本，以及可直接查看的差异说明。
2. 公式和规则映射：旧入口、候选入口、输入、输出、资源单位与副作用。
3. 风险清单：已复现、只由代码推断、设计口径待确认三类分开。
4. 接入说明：需要替换的调用点、对旧存档的迁移、回退办法。

原始 game.js、index.html、style.css、CHANGELOG.md 留在原处。候选代码未完成审查前不改变实际运行脚本。不要仅因函数名类似就合并价格、资源扣款、重置或时间函数。

## 建议的模块边界

- 数值核心：log10 权威值、double 缓存、零哨兵、带符号加减、饱和判定。所有资源经明确的读写入口处理。
- 价格与购买：每个升级保留原价格权威公式；纯报价库只返回级数与总价，提交层负责一次扣款、等级更新及冷却/次数副作用。
- 时钟与离线：在线和离线共用数值阶段；绝对虚拟时间负责真实秒公式；渲染、存档与输入留在模拟之外。
- 重置与迁移：湮灭、扭曲、虚空、卷缩、研究分别列出保留矩阵。迁移在原始存档字段可见时完成，失败不替换当前状态。
- 显示：只读取结果，不重新推导另一套价格或可购性规则；帮助和更新日志跟随确认后的公式。

当前项目是单脚本全局作用域，直接改成 ES Module 可能破坏 HTML 事件绑定和初始化顺序。因此先在 Review 中提取纯函数和候选适配层，经过调用点审查后再决定是否拆分运行脚本。

## 公式保护清单

| 主题 | 整理时不可丢失的条件 |
| --- | --- |
| 频率 | F=U/(L×膨胀倍率)^e；频率价的 U 扣款乘同一有效波长指数 |
| 资源 | 各资源的零哨兵不同；log 权威与 double 缓存的边界不能用通用赋值覆盖 |
| 购买 | 免费仍需门槛；普通/通胀、软上限与挑战条件分别定价；PG3 上限可能为小数 |
| 时间 | 真实时间与游戏时间分开；离线不自动增加“真实游玩时长” |
| 自动化 | 自动湮灭、升级 3 后回购、SAU/SBU/SVPU 与自动卷缩的顺序有玩法效果 |
| 重置 | AU、VPU、VP、黑洞质量、CM、理论树在不同重置中有不同保留规则 |
| 研究 | R9 深度、SR1 投入、实验预设与运行快照是不同状态 |

## 实施顺序

1. **保护存档：**先整理 S01、S02、S04 的迁移和时间字段，避免后续离线修改放大存档风险。
2. **购买库：**建立静态逆表与直接报价，消除 O(购买等级) 价格计算和每级购买副作用，再处理 N01、A01、A02。
3. **离线核心：**修正时间原点和 lastTick 语义，补共用数值阶段，再把重放拆成可让出主线程的小任务。
4. **局部数值修复：**按 Numerics.md 逐项处理 N02–N09；设计待定项独立停留在方案阶段。
5. **规则与显示：**处理 D01–D07，并同步帮助、注释和更新记录。

每项候选先以单独差异供审查，不把所有函数一次性重排。实施后的数值比较应覆盖旧存档、价格段边界、1e290/1e308、NLOG/LOG_CAP、自动重置和 8 小时离线；本次仅形成方案，尚未运行这些场景。版本名称在没有明确要求时保持原名；实际更新按默认要求提交并 git push。
